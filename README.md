# 服装零售门店销售诊断（自主数据分析项目）

用 **3 家门店、15 个商品、2,542 笔订单**（2026 年 7–9 月，共 6 张业务表）完整跑一遍零售数据分析链路：
MySQL 建库取数 → Excel 报表自动化 → Power BI 交互看板 → 销售诊断报告 → **库存补货调拨决策**。

## 核心结论

1. **9 月大盘回落 6.61%**，属三店共同的季节性回落；但**广州天河店环比 −11.76%、同比 −10.08% 为唯一异常**，跌幅是另两店的 3.7~4.7 倍。
2. **原因不是客流，是单客价值下降**：该店 9 月订单数 288 → 294（**+2.1%，逆势上升**），但连带率 2.080 → 1.884（**−9.4%**）、客单价 760.08 → 656.98（**−13.6%**）。
3. **直接诱因是主力高单价款断货**：该店 9 月三大主力款售罄率 **155.8% / 126.4% / 98.0%**（基本卖空），而同期佛山高明店同款仅 **9.5% / 13.6%** —— 不是货不够，是货没在对的地方。
4. **量化建议**：若该店客单价回到 8 月水平（760.08 元），以 294 笔订单计可多卖约 **3.03 万元**。

## 从「发现问题」到「给出清单」：库存健康度与补货调拨模型

上面的结论停在「建议调货」。为了让它可执行，我把库存表与订单表打通，建了一套补货 / 调拨决策模型
（`sql/06_inventory_replenishment.sql` + `excel/库存健康度与补货调拨建议表.xlsx`）。

**5. 库存呈「哑铃型」分布**：9 月 45 个「门店 × 商品」组合中，**断货 8 / 紧张 3 / 健康 12 / 偏高 13 / 积压 9**。
缺货的 11 个组合日均销量均值 **2.02 件/天**（全店最高档），积压的 9 个组合日均销量均值仅 **0.61 件/天**
—— 数据坐实了「好卖的没货、不好卖的压仓库」。

**6. 同一个款在不同门店可以差 297 天**：P003 商务西装在广州天河店周转 **−11 天**（断货），
在佛山高明店却是 **286 天**（积压）。这是典型的「店间错配」，可用调拨解决。

**7. 调拨只能解决错配，解决不了全网性缺货**：9 月共 **11 个「门店 × 商品」组合**缺货，门店级补货需求合计 **715 件 / 约 ¥260,485**。
其中跨店调拨匹配到 **2 条**（P003 商务西装 95 件、P010 中长款风衣 50 件），解决 **145 件**、释放库存价值约 **¥120,355**，且不产生采购成本；
剩余部分按全网口径复核（P009 A字半裙 40 件全网有货，只是富余店仅「偏高」档、未达 90 天调拨阈值），
**实际需采购 530 件 / 约 ¥131,470**。**先调拨、后采购**的优先级由此量化确定。

**8. 顺带做了数据质量校验**：按「期初 + 入库 − 销量 = 期末」对账，发现 **9 条负库存记录**
（7 月 1 条、8 月 3 条、9 月 5 条，涉及 5 个「门店 × 商品」组合），次月期初被系统回补至 15 件底线。
这 9 条不是脏数据，而是**断货超卖的业务证据**，恰好全部落在需求最高的款上。

## 数据说明

本仓库数据为**模拟生成**的教学数据集（3 家门店 / 15 个商品 / 2026 年 7–9 月 / 2,542 笔订单），
不含任何真实客户信息。方法链路完整，业务结论仅在本数据集内成立。
「去年同期」为用于演示同比口径的模拟值。

## 如何复现

1. 在 MySQL 中执行 `sql/01_schema.sql` 建表，再按 `sql/02_import.sql` 的说明导入 `data/` 下的 csv；
2. 执行 `sql/03_verify.sql`，6 项核对结果应与文件内注释的预期值一致；
3. 执行 `sql/04_business_queries.sql` 与 `sql/05_window_functions.sql`，得到 15 条业务查询结果；
4. 执行 `sql/06_inventory_replenishment.sql`，5 段查询分别对应「库存健康度与补货调拨建议表.xlsx」的 5 个 sheet；
5. 用 Excel 打开 `excel/Day4_Excel日报.xlsx`，点「数据 → 全部刷新」；
6. 用 Power BI Desktop 打开 `powerbi/Day5_看板.pbix`；
7. 诊断报告与作品集见 `report/`。
